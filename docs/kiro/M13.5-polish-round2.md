## 1. Org chart — visibility + confirm clickability

File: `src/app/(dashboard)/[orgSlug]/employees/org-chart/_components/org-chart-flow.tsx`

User: "the orgchart is nice but its super zoomed out and all bro, I want it
to be visible in a much better way and I want the people to be clickable
also."

Current state: nodes ARE wired with `onClick={() => router.push(...)}`
already (line ~130-131) — so clickability is likely NOT actually broken,
it's that `fitView` + `minZoom={0.3}` on a `600px` fixed-height container
squeezes a chart with more than ~8-10 nodes down so small that text is
unreadable and clicking a specific person is fiddly (tiny hit target). Verify
this theory by seeding/checking current employee count and rendering the
chart — don't assume, check.

Fixes:
- Raise `minZoom` floor so `fitView` never shrinks nodes below a legible
  size — e.g. don't let it go under 0.5, and if the computed fit-to-view
  zoom would need to go lower than that, let the chart overflow/scroll
  instead of shrinking further (React Flow supports this: don't force
  `fitView` to always show 100% of the tree at min zoom — cap it and let
  panning handle the rest).
- Make the container height responsive to viewport instead of a fixed
  `600px` — e.g. `calc(100vh - <header/breadcrumb height>)` with a
  reasonable min (e.g. 500px), so there's more room to work with on
  desktop.
- Add explicit zoom controls (`<Controls />` from `@xyflow/react`, it's
  built in) so the user can zoom in/out and fit-to-view on demand — don't
  rely purely on scroll-to-zoom which is easy to miss.
- Bump default node width slightly or increase font size at the default
  zoom level so names/titles are readable without zooming in first.
- Re-verify the click handler actually navigates in the deployed build (not
  just reading the code) — test by clicking a node with no unsaved zoom/pan
  state issues (React Flow sometimes needs `nodesDraggable={false}` +
  correct event propagation to not eat the click — confirm no regression).

## 5. Payroll complexity toggle — "Simple" vs "Advanced" mode

This is the biggest item — read carefully, this must NOT alter any stored
payroll data or break existing calculations.

User: "is it possible to kindof have a easy mode for this where all the
timings that they work is fixed and 9 to 5 but they can also enable to more
complicated version with the overtime and hourly rate and all. in that way
its modular but it doesnt like break the payroll data and calculations from
before if they wish to have it turned off first and then turn it on later."

### Design

Add an org-level setting, NOT a schema migration that touches existing
payroll/employee tables. Use the existing `OrganisationModule` table
(`prisma/schema/organisation.prisma:68`) which already has a
`settings Json @default("{}")` column, keyed by `moduleId`. Store:

```json
{ "payrollComplexity": "simple" | "advanced" }
```

on the `moduleId: "payroll"` row (create it if it doesn't exist for a given
org, default to `"advanced"` — see below for why).

**Default must be `"advanced"` for ALL existing orgs**, not `"simple"`.
Reasoning: M12 already seeded shift templates, `isWorkman` flags, and
`payType: HOURLY` for some employees, and payroll actions already branch on
`emp.shiftTemplate`/`emp.isWorkman` (see `src/modules/payroll/actions.ts`
lines ~96-259). If a fresh org row defaulted to `"simple"` and simple mode
suppresses that logic, every existing seeded org would silently change
payroll behavior on this deploy. Toggling to `"simple"` must be an
opt-in action the user takes in Settings, never an implicit default that
changes standing data.

### What "Simple" mode actually changes

Simple mode does NOT delete or null out `shiftTemplateId`, `payType`,
`isWorkman`, or any historical `PayrollRecord`/`PayrollLineItem` rows. It
only:

1. **Employee forms** (`employment-tab.tsx`, `employee-form.tsx`,
   `org-structure-panel.tsx` — find these under
   `src/app/(dashboard)/[orgSlug]/employees/` and
   `src/modules/employees/`, wherever M12 wired the shift/pay-type fields
   in) — hide the shift template / pay type / workman-status fields when
   the org is in `"simple"` mode. Existing values on the DB row are left
   exactly as they are (untouched, just not shown/editable). Employees in
   simple-mode orgs are implicitly salaried, working the org's default
   hours (`OrganisationSettings.workingHoursStart`/`workingHoursEnd`,
   which already default to `"09:00"`/`"17:00"` — this is your "9 to 5",
   it already exists as a schema default, don't hardcode a new one).

2. **Payroll run calculation** (`src/modules/payroll/actions.ts`, the
   payroll-generation function around lines 96-259) — when
   `payrollComplexity === "simple"` for the org, skip the entire
   shift/overtime computation branch unconditionally for every employee in
   that run (treat everyone as flat `compensationAmountCents`, no OT line
   items generated), REGARDLESS of what's stored on
   `emp.shiftTemplateId`/`emp.isWorkman`/`emp.payType`. This is a read-time
   branch on the org setting, not a data mutation — when the org later
   flips back to `"advanced"`, the stored shift/pay-type data is exactly
   as it was and overtime calculation resumes working immediately with no
   backfill needed.

3. **Already-generated `PayrollRecord`s are historical fact** — never
   recompute or touch past periods when the org's mode changes. Only
   future payroll runs are affected by the current mode at run-time.

### Where the toggle lives

Add it to the org Settings page (find the existing settings page/section —
`src/app/(dashboard)/[orgSlug]/settings/` — look for wherever other
module-level toggles or org preferences already live, follow that existing
pattern rather than inventing a new settings sub-page). A single labeled
switch: "Advanced payroll (shift templates, overtime, hourly rates)" — on
by default for existing orgs per above, with a short explanatory line ("Turn
off for a simple fixed-hours payroll. Your existing shift and rate data is
kept and restored if you turn this back on.").

Restrict changing it to whichever permission already gates
payroll/org-settings changes (check existing settings page for the
permission it requires, reuse it — don't invent a new permission for this
one toggle).

### Verification requirement

After implementing, you must be able to demonstrate: toggle an org to
"simple", run/preview a payroll calculation, confirm no OT line items are
generated and gross = flat salary; toggle back to "advanced" for the same
org, re-run, confirm OT line items reappear correctly using the
employee's still-intact `shiftTemplateId`/`isWorkman` — i.e. round-trip
with no data loss. State this test explicitly in your summary with actual
before/after numbers, not just "should work."
