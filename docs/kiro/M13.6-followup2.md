## 1. Org chart hover popover — z-index / stacking bug

File: `src/app/(dashboard)/[orgSlug]/employees/org-chart/_components/org-chart-flow.tsx`

User: "when i hover on it in the org chart, the hover thing sometimes shows
up behind someone else and im not able to read it."

Root cause: React Flow renders every node wrapper (`.react-flow__node`) with
`z-index: 0` by default, and DOM order (not visual position) breaks ties —
so a hover popover from one node can render underneath a sibling node that
happens to sit later in the DOM / lower on screen, even though the popover
has its own high z-index — that z-index is scoped to the node's own
stacking context, which is still `z-index: 0` relative to siblings.

Fix: when a node (or its popover) is hovered/focused, that node's own
wrapper needs to be promoted above its siblings, not just the popover
inside it. Add a scoped style rule bumping `.react-flow__node:hover` and
`.react-flow__node:focus-within` to a high z-index (e.g. `1000`) with
`!important` (inline styles need this to override), e.g. via a `<style>`
tag rendered alongside the chart, or a CSS module scoped to this component —
match whatever styling convention this component already uses (it currently
uses Tailwind utility classes + one `import '@xyflow/react/dist/style.css'`
at the top — a small inline `<style>` block in the same file is consistent
and keeps the fix colocated). Verify by testing a dense part of the chart
(multiple siblings at the same rank) and confirming the popover from a node
in the middle of a row renders above neighbors on both sides, not just one.

## 2. Sidebar has NO way to reach Settings at all — this is why the user couldn't find it

Files: `src/core/ui/shell/app-sidebar.tsx`, `src/core/ui/shell/app-shell.tsx`,
`src/app/(dashboard)/[orgSlug]/layout.tsx`

This is a real, pre-existing bug, not something the user is missing. Check
`src/core/modules/index.ts` and every `src/modules/*/manifest.ts` — grep for
`label: 'Settings'` — nothing registers it. `app-sidebar.tsx`'s footer does
`const settingsEntry = navEntries.find((e) => e.label === 'Settings')` and
only renders the footer Settings link if that's found — since no module ever
registers a nav entry with that label, `settingsEntry` is always `undefined`
and the link never renders, for any org, any role, always. The settings
sub-pages themselves (`/[orgSlug]/settings/profile` etc, including the new
Payroll Settings page from M13.5) all work fine once you're on the URL —
there's just no link into them anywhere in the app.

Fix: Settings isn't tied to an optional module the way other nav entries
are — it should always be reachable by anyone with `department.manage`
permission (the same permission every settings sub-page already requires).
Don't try to solve this through the module/nav-entry registry. Instead:
- In `layout.tsx`, compute `const canManageSettings = hasPermission(membership.role, enabledModules, 'department.manage')` (check the exact import path for `hasPermission` — it's used the same way in every settings page already, e.g. `src/app/(dashboard)/[orgSlug]/settings/profile/page.tsx`).
- Pass `canManageSettings` as a boolean prop through `AppShell` → `AppSidebar`, same pattern as the `storageUsedBytes`/`storageLimitBytes` threading added in M13.5.
- In `app-sidebar.tsx`, replace the `settingsEntry` lookup with this prop — render the footer Settings link (same styling/position it already has, same active-state highlighting logic) whenever `canManageSettings` is true, pointing to `` `/${orgSlug}/settings` `` (which already redirects to `/settings/profile`).
- Remove the now-dead `settingsEntry`/`mainNav` filtering-by-label-'Settings' logic if nothing else depends on it — check first.
